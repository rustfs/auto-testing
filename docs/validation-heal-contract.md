# Heal live validation design and acceptance contract

## Status and scope

This specification retains the source repository's 84 Heal canonical cases, 302 operation branches, and 534 applicable topology-branch templates. Resource requirements, the common pass criteria, and the per-item additional assertions must be satisfied together.

The entry points are `scripts/validation_heal/matrix.py`, the [per-case procedure cards](validation-heal-cases.md), and the [execution manual](validation-heal-operations.md). The runtime environment is the Heal nodes of the current auto-testing setup; the candidate and rc use the immutable packages and the actual binary digests of the current validation lane. Historical pilot results from the source repository cannot be counted toward this run's pass total.

All 84 Heal IDs already have dispatch routes, including 67 regular entry points, 13 environment-scenario entry points that are off by default, and four diagnostic entry points for C11/F07/I05/J02. Test-implementation completeness and product live results are counted independently: the source branches of C11/F07/I05/J02 already have execution flows; F07 combines manager interruption and directory fsync evidence for the same candidate, and the I05 controller serially executes the H1/H2 timeout and disconnect controllers and independently binds the full content/physical generation and the owner's native proof, as described in the [implementation review](validation-migration-implementation-review.md). The canonical acceptance gates of the four diagnostic entry points remain closed; a passing registered entry point or a passing native subset cannot stand in for a full PASS. Exact native checks and candidate admission for A09/G01–G06 are verified by their respective executors, and G06 already has a complete, independent live acceptance. A product FAIL does not automatically mean the test was not migrated. The shard executor checks the actual disk role, the file fault after the service is stopped, the raw digests of same-role shards, and per-block HighwayHash. A03 compares, via the original path/token, the task identity, terminal state, and full outcome of the H2 coordinator, an independent peer, and the fixed node entry; the startTime generated by the candidate on each response is not used as the task epoch. A04 retains four DB parameter combinations and two DV branches, requires the complete dry_run_observed set, and requires that objects are unchanged. A05 uses an independent deployment to execute all eight H1/H2 branches, freezes the actual merge configuration, a real non-zero running window, the exact conflict and token policy, and old/new task responsibility, and, after completion, proves while the service is running that every peer has exited and that the system is physically quiescent. A06/F06 prove physical quiescence after cancellation and isolation of the old token; F06 also retains the cancelled task's original persisted record, which must not be revived or overwrite a new task after restart. A08 retains the start/status/stop operations of each of the five principals, a genuinely expired signature, a temporary user authorized only for admin:Heal, and credential invalidation after cleanup. B09 uses a dedicated service with MRF explicitly enabled, records the degraded ACK while a node is offline, and validates the per-disk shard repair before executing the target S3 request. J03 must actually exceed the 1024-item retention window; a truncated diagnostic manifest still requires independent full physical/S3 corroboration. The 13 environment scenarios retain the source operation branches, the unmet conditions, and the explicit enablement entry points; their complete live validation still requires review of the resource adapter and the source assertions. The actual status of each item is in the [migration map](validation-migration-map.md); local checks, procedure cards, and archives cannot replace a live PASS.

The B03/B04 replacement runner first executes a read-only mount admission preflight before it is allowed to stop the service, download or install the candidate package, or create the remote run namespace. A blocking result explicitly records `execution_stage=pre-deployment`, the candidate/rc source, and `binary_sha256=null`, indicating that an installed candidate binary has not yet been observed. After the preflight passes, the deployment stage still reads the same set of mount and device identities again before reservation, so that the environment does not drift between the preflight and the actual change.

Of H07, the two single-set branches belong only to H3, and the two dual-set branches belong only to H4; the four mismatched combinations are recorded as `nonApplicableCombinations`. A missing machine is a resource block.

The goal is not only to prove that "GET still works after a disk goes bad", but to prove each of the following separately:

1. The fault actually occurred on the specified object, version, set, and target disk.
2. The customer-visible control interface and the expected trigger source handled this repair responsibility.
3. When recovery is possible, the target shard was actually repaired; when it is not, the failure is explicit and the damage is not widened.
4. Objects, historical versions, delete semantics, concurrent successful writes, and persisted responsibility are correct.
5. The raw evidence is complete, temporary faults have been cleared, and the environment can be handed back safely.

## Topology and fault domains

The table below is a **requirements model, not an inventory of machines that have already been allocated**. Every live action must go through the jump host and a fixed fleet lease. Azure VMs, disks, and networks must not be created or deleted privately. An existing example profile is not permission to run. The implementation must bind the node, port, service, mount UUID, disk count, pool/set/slot, and exclusive range, and must read back the actual EC metadata to confirm the layout.

| ID | Minimum shape / purpose | Current boundary |
| --- | --- | --- |
| H1 | One node, four independent disks, one EC set; basic disk repair | single-4disk may be used as a reference; use an independent heal service and a heal-validation root on each disk. Idle resources must be bound first, and existing Pool data directories are not reused. |
| H2 | Four nodes with four disks each, the same distributed pool, and an explicit fixed set division; cross-node faults, locks, and state | cluster-1pool may be used as a reference; the target set must be proven to span nodes, and the global node count alone is not sufficient. |
| H3 | Exact EC8+4, a single set, referencing the main repository's test shape of 3 nodes × 4 disks | This is a test parameter, not a production deployment recommendation; an old two-node Pool environment does not satisfy this topology. |
| H4 | Exact EC8+4 with at least two sets, referencing 3 nodes × 8 disks in the same pool | At least 24 independent disk endpoints and a correct set mapping; 4 disks or a single set must not be substituted. When the fixed resources have not been allocated, the result is blocked, not a pass. |
| H5 | Two or more pools; separately register the lifecycle shape of two nodes with four disks each, and the cross-node pool shape | The current lifecycle-a has one independent pool per machine and no node-level redundancy; it can validate disk-level repair and move interaction, and it cannot prove tolerance of a node failure. When aligning with the main repository's multi-pool EC8+4 baseline, separately register its layout of three single machines × 12 disks / three pools, and do not mix the counts. |
| H6 | An exclusive VM/host and a dedicated fault disk, able to perform a forced restart | Additional operations authorization, out-of-band recovery, and event evidence are required; a normal fault lane is not allowed to enter automatically. |

Production topology trade-offs may refer to the [RustFS Linux deployment guide](https://docs.rustfs.com/en/installation/linux): disk redundancy from multiple disks on a single machine is not whole-machine failure redundancy. Conclusions of this design hold only for the topologies that were actually validated.

For each object/version, record N, data/parity, the shard index, and the set/disk mapping in advance, then determine read quorum R, repair-write quorum W, and lock quorum from the candidate implementation and the metadata. Test the **legal combinations** of R-1/R/R+1 and W-1/W/W+1. Do not replace that calculation with the global number of online disks, or with a fixed assumption that "writes still succeed with half the disks bad". Shards across versions or across sets must not be added together; R and W are not necessarily the same. The N=1 no-EC capability and unrecoverable negative cases are additional parameter instances, and it must not be advertised that completely lost data can be recovered automatically.

## Fault backends and safety gates

Every injection must have a machine-readable fault-plan and fault-receipt. There is no rule that "a successful command means a successful injection". By default, each run isolates only one resolved target of this case, then expands according to the pre-registered combinations. Use the classes below. The report must record the actual faultBackend, and the classes must not impersonate one another.

| ID | Fault class | Injection validity and limits |
| --- | --- | --- |
| F0 | No fault; a pure interface request | Record a stable baseline; used only for no-side-effect and negative-request validation. |
| F1 | A specified part/shard is missing | First verify the exact path and digest, preserve it with an isolated same-disk backup or an atomic move, then prove that the target is missing; this is not a physical disk loss. |
| F2 | Specified bit flips, truncation, or checksum-header corruption | Operate on an isolated copy of the test object, and save the offset, length, before and after digests, and the original backup; enough undamaged authority must remain. |
| F3 | Specified xl.meta, inline data, identity, or bucket metadata is missing or corrupt | Requires a read-only parser that matches the candidate format, and an allowlist; IAM and credential configuration, the shared format, and unrelated objects must not be operated on. |
| F4 | The original logical disk or service volume is briefly unreachable or read-only | Use a restricted mount namespace or fault layer that affects only the test service, and actually verify that access fails. A shared XFS mount that contains data of other services must not be unmounted; chmod must not be treated as a valid fault until it has been verified. |
| F5 | Slow I/O, EIO, short reads, or ENOSPC/inode faults | Only on a pre-allocated exclusive test device or a fault layer with a capacity cap; a shared data disk must not be filled up. The difference between a simulated fault and a real device fault must be explicit. |
| F6 | Graceful stop, SIGKILL, and restart of the test process | Limited to the verified service and MainPID, and proven to occur inside a partial-progress window; record the boot and process identity. SIGKILL is not a power loss. |
| F7 | A network fault on inter-node test ports | Only for this service's address and port, a controlled namespace, or an exclusive environment, while protecting SSH, the jump host, and the management plane; rules carry a unique ID, a timeout, and idempotent recovery. |
| F8 | An empty replacement logical disk, with a new disk UUID | Verify the original and new disks and pool/set/slot; moving data back from a backup is not a rebuild. Real-device detach/attach additionally requires exclusive-resource authorization, and shared disks are not modified. |
| F9 | A deterministic fault in the checkpoint, commit, or lock window | Prefer a native runtime-fence or E2E barrier; when a Release black box cannot prove the exact window, list the native evidence and the live coverage gap separately. Do not insert a hidden test hook into an optimized package to impersonate the same candidate. |
| F10 | Forced restart of an exclusive VM/host | A separately approved destructive lane, with out-of-band recovery and a platform timeline. A VM forced stop does not prove the power-loss semantics of a physical controller cache. |
| F11 | Queue or request pressure, and faults in test KMS, tier, or quota dependencies | Acts only on the allocated test tenant or process, with limits on quantity and duration. A shared KMS or a remote service must not be disconnected globally. |

A fault-plan contains at least the run/case/variant ID, the topology fingerprint, the object/version/incarnation, pool/set/slot, the disk UUID, the exact file allowlist, the device and root-directory identity, the pre-injection conditions, the change budget, the backup digest, the recovery action, and the deadline for automatic fault clearance. Paths are resolved through directory descriptors. Link escape, device drift, unknown files, and free shell interpolation are rejected.

Clearing a fault and cleaning up data are two separate matters. Temporary environmental damage, such as network, read-only, or process faults, must be cleared safely. Failed data, shards, checkpoints, and evidence should be retained, the environment marked DIRTY/QUARANTINED, and the next case must not proceed. After evidence has been captured, business reachability may be restored by an approved procedure, but failure records must not be overwritten, and a recovery rerun must not be counted as the first pass. A backup may be used only for rescue or reset after a failure, and it does not take part in the repair-success verdict.

## Data fixtures and parameter dimensions

| ID | Content |
| --- | --- |
| DB | Deterministic baseline manifest: 128 objects by default, including 0/1 and 4095/4096/4097 bytes, plus the actual inline, EC stripe/block, and multipart boundaries ±1; confirm the shape from disk evidence, and do not hard-code internal thresholds. |
| DM | Completed multipart objects, parts of unequal length, and cross-part Ranges; also create pending/Complete/Abort fixtures with a traceable UploadId, observing the S3 minimum size for a non-final part. |
| DV | At least three versions of different content per key, current and historical delete markers, versioning suspended/null, and an explicit delete receipt; record versionId, Last-Modified, ETag, and the version list. |
| DS | Multiple buckets, adjacent prefixes, multi-page keys, encodings such as Chinese, spaces, and percent signs, metadata/tags/content headers, and isolated bucket configuration. |
| DE | SSE-S3/KMS/C and remote tier versions that the candidate explicitly supports and whose dependencies are ready; keys are supplied only through a controlled credential channel and must not enter logs or the manifest. |
| DO | Protected versions under object-lock, retention, and legal hold; use an expirable test policy so that a successful case does not permanently occupy the environment because it cannot be cleaned up. |
| DL | A per-request ACK ledger of concurrent PUT/GET/HEAD/LIST/COPY/DELETE, version, and MPU operations; each key uses an incrementing nonce and deterministic content, and the request, the response, and indeterminate results are saved. |
| DX | Fixtures that guarantee observable partial progress and exceed the status window (>128 items); the default upper bound is frozen in the run plan, soak and performance have a separate quota, and the test does not add data without limit while waiting for a chance hit. |

Parameterize by case/variant: normal/deep, data/parity shard, inline/external part, single shard/multiple shards, original disk/new disk, object/prefix/root/set, version/encryption, coordinator/target node, and single-node/multi-node/multi-set/pool. Use pairwise combinations frozen in advance to control scale. High-risk combinations, such as corruption plus quorum, an old generation plus concurrent delete, and target rebuild plus process interruption, must have explicit three-dimensional coverage, and pairwise does not replace them.

Non-default parity and storage class, and server-side compression on/off, that the candidate claims to support should also be added to the DB/DM/DV parameters. A Content-Encoding response header is not evidence that server-side compression was executed. Every instance confirms the encoded form from the actual metadata. An Object Lock rejection of delete must occur during a real retention period. Cleanup must not bypass Compliance, change the host time, or evade the restriction by deleting files internally. A legal hold is released only in the normal way by the test role authorized for this run. An instance whose retention exceeds the lane window must be allocated, in advance, an exclusive stateful environment and an expiry-handling plan. An environment that has not been cleaned up cannot be returned as READY.

A retry must not hide an ACK. A PUT or Complete timeout is an unknown result and must be resolved by querying the unique key, version, or UploadId. A write for which success was not received must not be treated as lost, and a new version produced by a retry must not be treated as the same success. Under concurrency, "the last one" is judged only from a provable happens-before or commit receipt, and not by ordering wall clocks across nodes.

## Common pass criteria (apply to every case)

The complete specification of each case row = this section + the corresponding topology, fixture, and fault contract + the in-row operation and additional assertions. Parameter instances are evidenced and scored independently.

1. **Preflight and baseline.** All expected peers and disks, and the candidate, rc, and harness identities, are consistent. GET, HEAD, and LIST the complete baseline in advance, and save the necessary on-disk records. Record the scan and automatic-heal configuration and the task ownership.
2. **Injection and witness.** Confirm, with read-only physical evidence, that the fault actually occurred and did not affect other objects or services. After injection, do not GET the target first and accidentally trigger read-repair. Acceptance that is too fast, or a repair already completed by another source, cannot impersonate a successful trigger of this case.
3. **Control-plane truth.** Collect every rc exitCode, the signed Admin HTTP status and body, and the token, source, scope, outcome, and peer coverage. Distinguish repaired, verified_healthy, metadata_healthy, authoritatively_absent, deferred, failed, unknown, cancelled, and dry_run_observed. deferred, failed, unknown, cancelled, and dry_run_observed cannot stand for "repair complete". `metadata_healthy` proves only that metadata and identity are healthy, and does not prove payload integrity. A Normal scan must not impersonate `verified_healthy`, and proof of a deep payload continues to require `verified_healthy`. The actual wire enumeration is taken from the pinned candidate.
4. **Object correctness.** Full GET of every object and version that must exist, verifying length, SHA-256, ETag, metadata, and tags. HEAD, paginated LIST, historical-version and marker semantics, confirmed deletes, and concurrent ACKs are all checked. A repair may produce legal internal metadata changes; the whole xl.meta is not required to stay byte-for-byte unchanged.
5. **Actual on-disk shard repair.** In the quiescent verification window, parse the target physical data and metadata, and check version, generation, data_dir, part length, bitrot checksums, and EC consistency. Data and parity each have an independent rebuild or re-encode comparison, or are corroborated by a fixed legal decoding set that includes the target shard. Counting files, looking at mtime, or relying on GET's automatic erasure-code fallback is not sufficient. A ciphertext or compressed storage layer cannot be compared directly with a plaintext digest. When the format is unsupported, or HighwayHash has not been verified, the gap must be stated, and deep physical acceptance must not be claimed as complete.
6. **Persistence and idempotency.** Cases that require a restart verify responsibility and data after the restart. A repeated heal does not introduce a new version, revive a delete, or increase tasks without bound. Status counts are distinguished by process, task, and epoch; a global count after a reset must not be judged as a regression on that basis alone.
7. **Completion conditions.** A positive repair requires the relevant responsibility to be complete, scope coverage to be complete, and the object evidence to agree with the physical evidence. An unrelated global idle, truncated list items, a missing peer, or unknown or leftover work still awaiting repair cannot substitute for that proof. Cases expected to be unrecoverable, denied by permission, cancelled, or dry-run pass against the pre-registered negative contract, and it is explicit that this is not a successful repair.
8. **Recovery and evidence.** Clear the temporary fault, save the four-phase before/fault/after/restart evidence, and check the global result, JUnit, plan, object counts, evidence references, and cleanup. Any missing evidence capture, a hit on the wrong target, a recovery failure, or a damaged result structure blocks that lane.

For an exact time window, activity, partial progress, or a controlled barrier must be observed before the fault is injected. An ordinary rebuild may finish quickly, but it must have evidence of actual on-disk shard repair. A fixed sleep, or "rerun until green", must not replace a witness. Suggested starting test budgets: 90 seconds for interface readiness, 15 minutes for ordinary repair, 30 minutes for restart recovery, and 5 seconds for the same-epoch quiescent window. These are **test budgets pending calibration, not a product SLO**, and every final budget must be frozen before the run. An expected transient error is retried only within bounds and only for an explicit code, and every attempt is evidenced.

Verdict types: a product safety, content, or terminal-state error is fail; a failure of environment injection or of an evidence-capture tool is infra_error; absence of a topology or auxiliary capability that has not yet been allocated blocks the run before deployment. A product SlowDown, or an expected error under low quorum, must not be generalized into infra_error. A missing required capability, an unknown option, or a missing parameter instance cannot be counted as PASS by way of unsupported or skipped. An inapplicable item may be stated only in the applicability manifest before the run. An environment that is not yet ready is not "not applicable".

## Execution method of the current framework

Functional Chain calls auto-testing's canonical dispatcher inside the shared-node concurrency lock. Ordinary live execution consumes the candidate deb and the tool artifacts and does not require a RustFS checkout. The read-only metadata inspector and the native barrier tests must bind the exact candidate source at build time and be evidenced separately.

Branches that are not yet automated are pinned by `matrix.py plan` for every applicable topology, source assertion, operation order, parameter binding, and recovery step. `matrix.py audit` checks the digests and branch completeness of the nine evidence classes. The results must still be reviewed item by item, and a canonical PASS is never generated on its own.
