# 批量删除回归用例

这些用例来自 main `0f9258594` 全量复测和后续批量删除诊断中发现的逐对象 `ServiceUnavailable`、准备/清理超时及热点并发问题。用例验证 S3 可观察行为；RPC 内部的迟到响应、exact-ID 清理和按键重试仍由 RustFS 锁库的回归测试验证，不能仅凭外部请求成功声称内部缺陷已修复。

## 用例与判定

| 用例 | 子场景 | 通过条件 |
|---|---|---|
| S3C-213 BulkDeleteBatchMatrix | 版本关闭/开启/暂停 × 1、32、128、500、1000 键，共 15 项 | 一次请求中每条输入均有结果、无逐对象错误；各端点均看不到已删当前对象；未参与删除的对象字节不变；开启和暂停模式下保留抽样历史版本的原始字节。 |
| S3C-214 BulkDeleteDuplicateKeys | 三种版本状态，共 3 项；包含同一键重复 16 次和两个重复的不存在键 | 按输入条目数核对响应，不把重复条目当作独立对象；当前键删除且控制对象、历史版本保持正确。 |
| S3C-1306 BulkDeleteUnderGetLoad | 三种版本状态，共 3 项；默认 32 个读取工作线程和 1000 键删除 | 所有线程先成功读取控制对象；并发负载期间读取字节保持一致；一次批删无错误、无当前对象残留；所有传入端点均验证结果。 |
| S3C-1307 BulkDeleteWriteRecovery | 三种版本状态，共 3 项；默认 32 个有限写入线程、一个热点键和 127 个其他键，热点键在批删输入中重复 16 次 | 原始请求及负载无错误、其他键删除；竞争结束时热点值不存在或为完整已写入值，各端点视图一致；随后同键 PUT、各端点 GET、DELETE 及其他键重试成功，最终无当前对象残留。 |

默认每个拓扑执行 24 个子场景，全量 S3 套件的三个拓扑共执行 72 个子场景。对象体为 128 KiB，最大单批种子数据约 125 MiB，不复用压测中的历史大桶。每个子场景使用新建的独立桶，清理显式移除对象版本、删除标记及未完成分片上传，再检查没有残留并删除桶。不会删除其他桶、修改节点配置或注入环境故障。

原始批删只发起一次请求，SDK 自动重试关闭。HTTP 200 的 `DeleteResult/Errors` 是失败；顶层 HTTP 503 响应数和逐对象 `ServiceUnavailable` 条目数分别记录，不能互相换算。恢复或清理重试成功不会覆盖原始失败，清理曾出现错误的子场景也保持 FAIL。一次调用中清理最终失败或中断时，该调用的后续子场景记录 NOT_RUN，保留责任与证据；全量拓扑套件其他独立用例沿用原有调度。

热点用例在记录原始请求失败后继续验证无负载恢复，分别保留原始失败和恢复结果。故意制造高负载下的合法仲裁超时仍会使严格回归判定失败；失败结果是需要调查的现象，不能自动认定每个 503 都是同一种产品缺陷。

两个负载场景均在所有工作线程完成预热后释放后续请求，并等待至少一个实际 SDK 调用进入，再发起原始批删。只有预热之后成功的 GET/PUT 调用与批删调用在客户端的单调时钟区间存在正交集，负载条件才通过；仅预热成功、所有请求提前完成或重叠请求全部失败都不能通过。GET 的区间包含响应体读取，客户端创建、PUT 响应后的日志写入和批删响应完整性核对不计入请求区间。结果记录重叠成功次数、工作线程数和首个交集，事件文件保留每次交集；这些是客户端并发证据，不是服务端锁重叠的证明。

HTTP 200 响应即使漏掉部分输入，也会先保存已解析的删除确认和逐对象错误，再以 `IncompleteDeleteResponse` 判失败。恢复阶段自身失败时保留原始阶段的独立结果；原始验证中的流式读取超时或短读也会记录为失败，然后继续热点键的无负载恢复检查。

## 执行与证据

全量入口为 `rustfs-s3-compat-test.sh --all-topologies`，也可以使用 `--cases S3C-213,S3C-214,S3C-1306,S3C-1307` 选择这些用例。`--bulk-delete-results-dir DIR` 指定持久证据目录；未指定时创建独立目录，有日志文件则放在日志旁边。多节点拓扑使用既有入口和配置的其他节点地址直接验证。S3 workflow 在本次任务的独立 venv 中安装 boto3，避免修改宿主 Python 包，并自动上传结果目录；手工执行时可通过 `RUSTFS_S3_BULK_PYTHON` 指定已安装 boto3 的 Python 解释器。

已经部署的集群可以直接运行以下命令。凭据使用 `RUSTFS_ACCESS_KEY`/`RUSTFS_SECRET_KEY` 或 `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` 环境变量；令牌对应 `RUSTFS_SESSION_TOKEN` 或 `AWS_SESSION_TOKEN`。调用方必须在整个测试和清理期间持有环境共享锁。

```bash
python3 scripts/s3_bulk_delete_regressions.py \
  --endpoint http://node1:9000 \
  --endpoint http://node2:9000 \
  --endpoint http://node3:9000 \
  --endpoint http://node4:9000 \
  --result-dir /absolute/path/to/new-results
```

默认准备预算 300 秒，请求/验证/恢复各阶段预算 60 秒，负载预算 30 秒，清理预算 180 秒；通过 `--prepare-budget`、`--request-budget`、`--load-budget`、`--cleanup-budget` 调整。每阶段各端点共用一个截止时间，不允许后续请求重新获得完整预算。客户端连接和读取设置有界超时，负载线程执行有限轮次；网络读取超时是 socket 读取超时，不应解读为逐字节流的硬墙钟限制。

每个负载线程复用自己的客户端与连接池；剩余预算不足其 10 秒读取超时后才重建并收紧超时。共享性能工具仍保持原有 60 秒读取超时。

每个子场景保留 `result.json`、`s3-events.jsonl` 和 `bucket.s3.json`。结果包含第一失败阶段、后续失败列表、各阶段耗时、请求 ID、SDK 重试次数、各阶段 HTTP 503 响应数、逐对象错误条目、内容校验和清理结果。`summary.json` 和中文 `summary.md` 汇总全部计划子场景及未执行项。结果目录必须全新，禁止用后续运行覆盖原始证据。

## 本地验证范围

`python3 -B -m unittest test_s3_bulk_delete_regressions.py` 使用响应变异和版本模型验证通过/失败判定、重复输入计数、历史版本保留、泄漏检测、失败后恢复、阶段预算、清理失败历史、中断证据和全量入口选择。这些测试验证测试工具本身，不等同于 RustFS 测试机复测通过。性能准备/清理中断和报告前后超时的既有回归继续位于 `test_rustfs_performance_testing.py` 与 `test_performance_s3.py`，避免重复编写同一套模拟。
